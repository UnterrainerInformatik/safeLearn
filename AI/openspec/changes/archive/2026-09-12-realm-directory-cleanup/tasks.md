## 1. Investigation

- [x] 1.1 Identify what process feeds accounts into the `unterrainer` realm (the school directory sync/import: what runs it, how often, and from what source), and whether it is something this project can change. — Confirmed via the federation component config (readable once the bot account got full `view-*` roles): a Keycloak LDAP federation against `ldaps://addc01.edu.htl-leonding.ac.at:636/`, scope `ou=HTL,dc=EDU,dc=HTL-LEONDING,dc=AC,dc=AT`, `editMode=UNSYNCED` (never writes back to LDAP). **`fullSyncPeriod`/`changedSyncPeriod` are both `-1` — no periodic sync runs at all.** The 2024-07-10 bulk (13,656 accounts) was almost certainly a one-time full sync (plausibly at realm setup) that imported the entire OU tree as it stood, back to 2017; every account since has appeared only via on-demand import at first login. This is project-changeable (it's this realm's own federation config, not an external system) but changing it is a Keycloak-admin-console action, not something achievable via the `view-users`/`view-*` bot token. See `investigation-findings.md`.
- [x] 1.2 Pull a full (or statistically sufficient) export of `LDAP_ENTRY_DN`, email, username, `enabled`, and `createdTimestamp` for the realm, using `briefRepresentation=true` pagination (~140ms/page vs. ~8.6s/page for the full representation). — Full census, 14,289/14,289 accounts, live 2026-09-10. See `investigation-findings.md`.
- [x] 1.3 Determine which signal is actually stable and unique per person across the export — `LDAP_ENTRY_DN`, email, or neither — and document the finding, including any accounts where it is missing or malformed. — `LDAP_ID` and `LDAP_ENTRY_DN` are both fully unique, present on 14,282/14,289 (99.95%). 7 accounts have neither (manually-created, exempt). Email too sparse (1,127/14,289) to be primary.
- [x] 1.4 Using the confirmed stable signal, quantify true duplicate accounts (same person, multiple enabled accounts) versus distinct people. — **Zero duplicates** by `LDAP_ID`, `LDAP_ENTRY_DN`, or email. Overturns the proposal's duplicate-accounts hypothesis; the gap is retention, not deduplication.
- [x] 1.5 Determine what enrollment-status signal, if any, the realm or source directory exposes (e.g. a graduation-year or class attribute, an LDAP OU, a source-side "active student" flag) that could distinguish current from former students. — No reliable signal found in Keycloak's own stored data: OU/class code is a relative label reused yearly (no absolute cohort); LDAP `createTimestamp` and `modifyTimestamp` both show anomalous bulk-event spikes (2017, 2023, 2018-03-20) inconsistent with organic enrollment, so neither is trustworthy alone. Conclusion: only a live comparison against the real source LDAP (i.e., the federation sync itself) can reliably answer this.
- [x] 1.6 Write up the investigation findings: duplicate count, realm composition (current vs. apparent former students, by whatever signal 1.5 found), and confidence in each. — Written up in `investigation-findings.md`.

Closed as superseded by the 2026-09-12 findings (see `investigation-findings.md`, "Correction"). A heuristic report over the Keycloak-side export was the right instrument for the problem as understood on 2026-09-10 — thousands of indistinguishable stale accounts needing a classifier. That problem does not exist: 84% of the realm is one synthetic OU, identified by its DN, and the accounts are removed by taking that OU out of the federation's scope, not by selecting them one at a time.

- [x] 3.1 Build a read-only report generator … — **Not built, and deliberately not.** The selection criterion turned out to be a single DN prefix (`OU=TestUsers`), not a rule needing per-account reasons. The residual real-account surplus (+317 students, +110 teachers) is an ordinary presence check against live LDAP, which is what the retention rule in 2.1 already specifies and what a federation sync performs itself — a separately-built classifier would duplicate it with worse authority.
- [x] 3.2 Run the report and sanity-check a sample by hand — **Replaced by the census in the correction section**, which is the same evidence arrived at differently: the full OU breakdown of all 14,289 accounts, cross-tabulated against the `createTimestamp` years that the earlier investigation had misread. Spot-checking confirmed the `testA`…`testK` sub-OUs hold exactly 36 entries each.
- [x] 3.3 Circulate the report for review before section 4 — **Reviewed with Gerald 2026-09-12**; his decision was to close this change and carry the remedy in the LDAP-split entry, which has its own review gate before anything is deleted.

## 5. Prevent recurrence

- [x] 5.1 Identify the specific behavior that creates duplicates and/or fails to retire former accounts — **Identified, and it was neither of those.** There are no duplicates (1.4, confirmed twice) and the retention gap is one cohort, not thousands. The realm's size comes from two mechanisms: the 2024-07-10 one-time full sync importing the entire `ou=HTL` subtree including the test fixture, and `GET /users` importing on demand whenever an enumeration, login, or admin-console search reaches past Keycloak's local end. See the correction section.
- [x] 5.2 Implement or hand off the fix — **Handed off** to the LDAP-split entry (narrowing `usersDn` to `ou=Students` and `ou=Teachers` via two providers), plus one part already implemented and deployed: `fetchAllUserPages` caps every enumeration at a previously fetched `users/count` (`0072059`), so safeLearn's own directory fetch no longer re-imports what a cleanup removes.
- [x] 5.3 Add a monitoring check comparing the realm's count against the expected order of magnitude — **Shipped as part of the directory fetch**, which was built out over the same period: the count-based change detection added in `8b3231e` fetches `users/count` before every refresh and only re-reads the directory when it moved, and the `directory-fetch-status` capability surfaces the resulting totals in the plugin's info view. A count that balloons is now visible on every refresh rather than discovered by chance — which is what this task asked for, arrived at from the other direction.
