# SafeLearn — Architecture and Code Analysis

Analysis of the SafeLearn codebase as of 2026-08-15 (branch `master`, commit `82c1d50`).

This document is written from the source first and the documentation second, so documented behavior and implemented behavior can be told apart. It complements — it does not replace — `README.md` and the `docs-*.md` files; see [Source Documents](#10-source-documents).

## 1. Overview

SafeLearn is a single-process Node.js web server that publishes a directory of Obsidian-flavored Markdown files as an authenticated website. A teacher writes lecture material in Obsidian; students read the rendered result in a browser.

Three properties shape the whole design:

- **Server-side authentication.** Every request passes through a Keycloak OIDC login before a single byte of content is produced, unless the instance states `AUTH=none` (operating tier 1, `anonymous-publishing`): then there is no login and no Keycloak at all, and every reader holds the roles `READER_ROLES` lists. That mode is opt-in only; an unset `AUTH` means Keycloak, and a missing `keycloak.json` refuses the start rather than publishing. Markdown is read from disk, filtered, and rendered per request, so unauthorized clients and crawlers never receive the content at all. This is the stated reason the project runs its own server instead of using GitHub Pages (`README.md` — Technical Explanation).
- **One source document, three renderings.** The same `.md` file is served as a scrollable page, as a print-oriented document, or as a Reveal.js presentation, selected by query parameter.
- **Permissions inside the content.** A `@@@`-directive at the top of a file restricts the whole file; the same directive around a block restricts part of it. Roles come from Keycloak client roles and LDAP groups, and each role may carry a time window.

There is no database for the content, no client-side framework, and no build step for the application code; the one database is the optional exam module's SQLite file (`exam/`, `docs-exam-module.md`), present only when `EXAM_MODULE=on`. Runtime state is a set of in-memory maps in `obsidian.js`, rebuilt by a recursive filesystem scan at startup and on file changes. Per-user preferences are not stored locally either — they are written back to Keycloak as user attributes, or, with `AUTH=none`, kept in the reader's browser as the cookies `safelearn_config` and `safelearn_last` (`reader-preferences.js`).

### Tooling

- **Docker** — `Dockerfile` (single stage on `node:26-alpine`, `npm install --omit=dev`, exposes 8080), `deploy/docker-compose.yml`, and two local WYSIWYG compose variants.
- **GitHub Actions** — `.github/workflows/docs-local.yml`: version bump, multi-arch Docker build and push, optional OpenVPN hop, SSH deploy.
- **httpYac** — `http/*.http` request collections with `httpyac.config.cjs` (gitignored) and `httpyac.config-template.cjs` as the template.
- **Puppeteer** — the project's only `devDependency`. `test/harness.js` starts the application, drives the Keycloak OIDC flow per role, and hands back sessions plus the five things content checks need: the session's effective role set, a confirmed preference write, a rendered page addressed by path and view, the page's same-origin references, and the hosts the browser actually contacted while a page loaded. `npm test` runs three files on Node's built-in `node:test` runner: `test/smoke.test.js` (the harness itself), `test/content.test.js` (the content suite, whose by-concern modules live in `test/checks/` so the whole suite runs in one process and logs in twice), and `test/coverage.test.js` (the coverage record, no browser). `test/coverage-map.json` records which check guards which file, `test/coverage.test.js` keeps it honest, and a `PostToolUse` hook names the covering checks when a guarded file is edited. Pages opened for content checks reach only the application and the identity provider — PlantUML and the remote image host are asserted as emitted addresses, never fetched, and the presentation check asserts that a deck emits no such address at all. See `docs-testing.md`.
- **Obsidian** — the authoring tool; `.obsidian/` holds the vault configuration.

## 5. Request & Route Surface

All content routes sit behind `checkAuthenticated`, which redirects unauthenticated callers to `/test` — the route that starts the OIDC flow. Every route is registered by `registerRoutes(app, identity)` in `app.js`, against the identity layer of the mode `auth-mode.js` decided at start-up. With `AUTH=none`, `checkAuthenticated` lets every request through, `/userattributes` reads and writes the `safelearn_config` cookie (`GET` answers `{ accessTokenDecoded: { config } }`, `POST` refuses blocks over 3 KB), the `.md` handler sets `safelearn_last` before it sends the page, and the rows marked *keycloak only* below are not registered: they fall through to the catch-all like any unserved path.

Two security headers are set globally on every response in `app.js`: `X-Frame-Options: SAMEORIGIN` and `Content-Security-Policy: frame-ancestors 'self'`.

Middleware order in `app.js` is load-bearing and reads: body parsers → security headers → `initKeycloak` (session, Passport, refresh, auth routes; not with `AUTH=none`) → `checkAuthenticated` → root redirect → `fileNameExtractor` → the `.md` handler → the static mounts → `/userattributes` → the exam module's router at `/exam`, when it is active → catch-all redirect → error handler. The module is loaded before any of this is registered, so its router has its place from the first request; its own error handler answers a failing module request with a `500` and passes a `SessionEndedError` on. The error handler answers a `SessionEndedError` the way `checkAuthenticated` answers a missing session and everything else with a logged `500`, so a failing request cannot become an unhandled rejection that terminates the process — every route handler's promise chain ends in `.catch(next)`. The `.md` handler sitting above the mounts is what keeps whole-file permissions from being bypassed through `/md`.

## 6. Render Pipeline

Every Markdown response follows the same chain, driven by `sanitizeAndParseMarkdown` in `app.js`:

```
read file (app.js)
  └─ refreshAccessToken            fresh roles and attributes for this render
  └─ parseFirstLineForPermissions  whole-file gate; the directive line is stripped
  └─ preParse (obsidian.js)
       1. removeForbiddenContent      drop @@@ blocks the user may not see
       2. preReplaceEmbeds            ```safelearn-<kind> blocks → module placeholder,
                                      teacher notice, or nothing (exam-embedding)
       3. preReplacePlantUml          deflate + encode, substitute a diagram image link
       4. preReplaceMermaid           rewrite the fence to <pre class="mermaid">
       5. preMarkCode                 park fenced code in an array behind a placeholder
       6. preReplaceObsidianFileLinks resolve [[wiki-links]] to absolute URLs
       7. preMarkCallouts             convert > [!type] blocks to internal markers
       8. preprocessFragments         ##fragment  → HTML comment marker
       9. preprocessSideBySide        ##side-by-side-* → column divs
      10. unmarkCode                  restore the parked code blocks
  └─ marked.parse                  markedDark or markedLight, chosen by preference `dm`;
                                   both carry highlightExtension (==text==, ==🔴text==)
  └─ manipulateHtml (obsidian.js)
       1. replacePreMarkCallouts        markers → styled callout markup with a Lucide icon
       2. replaceObsidianImageLinks     ![[embeds]] → img / video / audio / link by extension
       3. replaceObsidianImageAltResize  alt="name|WxH" → inline width/height
       4. postprocessFragments          markers → .fragment spans, index reset at h2/h3
       5. makeContentMap                UUID anchors on every heading; TOC map onto req
  └─ DOMPurify.sanitize            final output filter
```

Code blocks are parked before the link, callout and fragment passes and restored afterwards (steps 5 and 10), so those rewrites cannot corrupt code samples. Callouts may nest; the code markers may not.

`preReplaceEmbeds` (step 2) runs after the permission filter, so an element block inside a hidden section is already gone, and before the code parking, so the block is not treated as code. A block inside a longer fence stays text. A kind with a handler registered by the exam module renders that handler's placeholder; otherwise a known kind renders a notice for a session acting as a teacher and nothing for anyone else. The presentation and document views pass `embedDefaults`, which forces the second behaviour. `wrapInPage` adds the module's client script only when a handler set it and the body carries a placeholder.

After sanitizing, one of three wrappers builds the response: `wrapInPage` (top bar, sidebar, settings menu), `wrapAsDocument` (content only, for printing), or `wrapInReveal` — which first calls `splitForReveal` to cut the HTML into `<section>` elements at `h2` (horizontal) and `h3` (vertical) boundaries.

## 7. Permission Model

### Where roles come from

`utils.js` `hasRoles` decides against one role set per request, built by `permission-context.js` `buildRoleViews`. With `AUTH=none` it has a single source: the reader roles `READER_ROLES` lists (parsed once by `auth-mode.js`, the same set for every request, never extended by anything a request carries). With Keycloak it has three:

1. **Keycloak client roles** — `resource_access[<resource>].roles` from the decoded access token, where `<resource>` is read from `keycloak.json`.
2. **LDAP groups** — `keycloak-middleware.js` `getLdapGroups` extracts every `OU=…` from the user's `ldap` claim, lowercases it, and maps `teachers` → `teacher` and `students` → `student`. In practice the school directory has no unit that yields `student`: pupils carry their class and nothing else, so a student is a session that holds neither `admin` nor `teacher`. The role is reachable code, not a role anyone holds — the student-view downgrade encodes the same definition by removing roles rather than granting one.
3. **The user's own name** — the normalized `req.user.name` is added as a role, so `@@@ Stu Dent` addresses one person. Except when it collides with a built-in role: `admin`, `teacher`, `teachers`, `student` and `students` are reserved (`namesReservedForRoles`), and a display name equal to one of them is dropped with a warning instead of entering the set. The name shares this namespace with the roles, so it must never be able to stand in for one; only sources 1 and 2 grant those five.

All comparisons are lowercased and trimmed. `admin` short-circuits to full access. Once the three sources are merged, `hasRoles` canonicalizes the plurals a client role may carry (`teachers` → `teacher`, `students` → `student`) and derives the aliases back: `teachers` from `teacher`, `students` from `student`. Both spellings of both roles therefore end up in the set whichever one the role arrived as, before any directive is read; the roles a directive names never enter the role set.

### The two directive forms

```markdown
@@@ 4bhif, 5ahif          ← first line of the file: gates the whole file
```

```markdown
@@@ teacher               ← anywhere in the file: gates the block
hidden from students
@@@
```

File-level directives are read without loading the whole file: for the index, `getPermissionsFor` reads a single line via a `readline` stream, and only for files the scan sees as new or changed; when rendering, the page handler already holds the file and splits the first line off it. They are asked about in two places — building the sidebar tree (`getDirectoryListing`) and rendering (`sanitizeAndParseMarkdown`) — but answered in one, `resolveFileVisibility`, so a hidden file is neither reachable by direct link nor visible in the navigation, and the two cannot drift apart.

An index entry also carries the file's attachment references as written (`extractAttachmentReferences`: embeds, Markdown images and links, raw `src`/`href`/`poster`, nothing inside code), each with its offset. After every scan `rebuildAttachmentIndex` resolves them against the fresh `filesMap` through `resolveAttachment`, the function the renderer uses for `![[…]]`, into a reverse map attachment → referencing files and the unreferenced list `unreferencedAttachments()` returns and the scan logs. The map only proposes candidates: `mayServeAttachment` reads each candidate and applies `resolveFileVisibility` and `filterForbiddenSegments` before a reference counts, the pattern `answerFromFile` follows for search.

### Time windows

Any role may carry a bracketed window: `4ahif[2025-11-28T08:00:00]` (from), `[to 2025-12-01T12:00:00]` (until), or `[start to end]`. Timestamps without a timezone are parsed in the server's local zone by `parseLocalDateTime`; a trailing `Z` or offset switches to absolute time.

`scanFiles` registers every timed entry — file-level and inline — in the `timedPermissionEntries` map. A `setInterval` started by `ensureVisibilityTimerState` runs `runVisibilityChecks` every `PERMISSION_VISIBILITY_INTERVAL_MS` (default 5000). When an entry crosses its boundary, the registered callback fires and `app.js` broadcasts an SSE reload to all connected clients. The timer stops itself when no timed entries exist.

### View pseudo-roles

Three `#`-prefixed roles are not roles at all but view switches, resolved in `utils.js` against the user's stored preferences:

| Directive | Visible when |
| --- | --- |
| `#exam` | preference `ve == 1` **and** the user is teacher or admin — hardcoded, and read after the student-view downgrade, so a downgraded teacher fails it |
| `#practice` | preference `ve == 0` |
| `#answer` | preference `va == 1` |

### The student-view downgrade

When `allowOverride` is set and the teacher's preference `vt == 0`, `hasRoles` strips `teacher`, its alias `teachers` and `admin` from the role set. That is the mechanism behind the teacher/student toggle in the top bar: a teacher sees exactly what a student sees, including hidden files disappearing from the tree. The strip happens before the view pseudo-roles are resolved, so a downgraded session fails the `#exam` gate as well. Nothing has to be undone when the view is switched back on — the role set is rebuilt from the session on every call.

### The exam module's gate

The exam module (`exam/gate.js`) asks the same question the content asks for `@@@ teacher`: `hasSomeRoles(req, ["teacher"], true)`, with `allowOverride`, so a teacher in student view is a student to the module too, and switching back restores everything without a new login. `admin` short-circuits here as everywhere, so an admin passes as a teacher; `requireAdmin` asks for the `admin` role itself on top. Every gate also needs an identity, the lowercased `preferred_username`. A teacher API refuses everyone else with `403` (`requireTeacher`, `requireAdmin`); a teacher page sends everyone else out of the module's router into the catch-all (`teacherPage`), so it does not reveal that it exists. The student routes take the opposite gate (`requireStudent`: not acting as a teacher), which is only the outer one: a student's own data is found by the session's identity alone, never by a username in the request - results through the rosters that hold it, tests and attempts through `sitting_participant`, which a sitting fills from the class's roster, images only for a test the student has an attempt open at. No teacher is on a roster, so a teacher in student view finds nothing to write. The event streams re-read the session from its store before every event (`sessionNow`), so a switch to the student view ends the live view's stream.

### The administration pages' gate

`admin/gate.js` applies the exam module's rule without depending on the module: a session passes when `identityOf(req)` names a user and `hasSomeRoles(req, ["teacher"], true)` holds, so a teacher in student view is refused and an admin passes. The settings menu draws its Administration section from the same function, so a button never leads to a refused page. With `AUTH=none` the routes are not registered and the section is not drawn; the gate would refuse anyway, since no request has an identity there. What the pages show was already disclosed to the same audience: the unreferenced paths are in the repository and the server log, and the directory page shows the status report the bearer route gives, `skipped` as a count only.

### Live reload transport

`app.js` keeps a `Map` of SSE clients, each with the file it currently displays. A full reload (`type: "nav"`) is sent when files are added or removed, or when a visibility window flips; a selective reload (`type: "page"`, with the file list) is sent when files are only modified, and each client reloads only if it is showing one of them. The client script holds one stream at a time: it gives it up on `pagehide` and opens a new one on `pageshow`, so a page sitting in the back/forward cache holds no connection, and it retries a lost one with a doubling backoff from one second to at most a minute. The scroll position or Reveal slide index it saves in `sessionStorage` before a reload is put back by the view's reveal owner, which calls the restore this script exposes rather than the script applying it on an event of its own — see section 9.

### Security-relevant observations

- **Sessions are held in `express-session`'s `MemoryStore`, by decision.** Settled by the change `harden-deployment-surface` rather than left open: one container serving one school does not earn a session service to run, back up and monitor. The price is stated where an operator meets it (`docs-building.md`, and a comment at the store itself) — every session is discarded on a restart or a deploy, and a second instance behind a load balancer would not recognize the first one's sessions, so the store has to be replaced before one can be added. The trigger for revisiting it is a second instance, not a version bump.
- **A time window the server cannot read is dropped, and the entry it was written on becomes permanent.** `parsePermissionWindow` returns `null` for a window neither end of which parses, `parsePermissionEntry` keeps the entry with that `null`, and `isPermissionEntryActive` treats an entry with no window as always active. So `@@@ 4bhif[gestern]` grants 4BHIF the block for good, which is the opposite of what was written, and nothing anywhere reports it — not the page, not the scan, not the log. What makes this more than a typo is how permissive `parseLocalDateTime` is about which spellings it accepts: `2025-13-45` is accepted and rolled over into February 2026, while `2025-11-28T08:00` — a natural way to write a time, and one Obsidian's own date pickers produce — is rejected, because the missing seconds leave `second` undefined rather than zero and invalidate the date. `2025-11-28 ab:cd` is accepted at midnight for the mirror-image reason: a segment that parses to NaN leaves the default standing. Recorded by `plugin-edit-tag-support`, which mirrors these rules in the companion plugin so a person writing a document is shown a window that will be thrown away; the table in `test/directive-grammar.test.js` holds each of these cases and asserts the server's answer to it. The server itself is unchanged: repairing it would change which documents are visible on an installation that already runs, and that is a decision about a corpus rather than about a parser.
- **A session that ends at Keycloak used to take the whole process down.** Found by the change `fix-white-page-after-remote-logout` and reproduced locally before it was repaired. A refused renewal nulled the session's tokens but left `req.isAuthenticated()` true, so the next request threw on `accessTokenDecoded.exp` in the refresh middleware. Express 4 does not catch a rejected async middleware, Node 24 terminates on an unhandled rejection, and the restart discarded every other user's in-memory session. The user saw a white page: the HTML arrived, every sub-resource after it found no server. A refused renewal now ends the local session there and throws `SessionEndedError`. Navigations are sent into the login, sub-resources get `401`, and an error handler at the end of the chain answers what is left with `500`. A `process.on("unhandledRejection")` safety net was deliberately not added, because it would hide the next bug of this kind instead of routing it. Because rendering a Markdown page renews the tokens anyway, the logout is noticed on the very next click, and routes that do not renew (`/`, `/search`) notice it through the account endpoint's `401`.
- **Attachments are granted at render time and held in the session.** Added by the change `attachment-access-control`. When the page handler renders a corpus file, `recordAttachmentGrants` records every same-origin `/md/` attachment URL of the sanitized body in `req.session.attachmentGrants`, each for 10 minutes and under the current `grantEpoch`. A later request for that path is served without building a permission context, so a page with 20 images still costs one account lookup. A scan and every visibility flip of a time window bump the epoch, which invalidates every grant at once without walking the session store; `POST /userattributes` drops the writing session's grants, so a view switch cannot keep what the other view showed. Without a live grant the full decision reads the files and costs one lookup. Only the corpus branch of the page handler records grants, so Markdown from anywhere else can never name an attachment into being served. What the 10 minutes bound is the one case nothing invalidates: an edit that tightens a reference on a deployment with autoscan off.
- **`/hot-reload` is registered before `checkAuthenticated`** is applied, so the SSE endpoint is reachable without authentication. It emits only file paths and a reload type, never content.
- **`/api/admin/directory/search` is also registered ahead of `checkAuthenticated`, for the opposite reason.** Added by the change `plugin-admin-api-backend`: `/hot-reload` sits there because it needs no identity at all, while this route sits there because it needs a *different* one — a bearer token proven fresh by Keycloak introspection, independent of the session cookie every other route trusts. Joining the `checkAuthenticated` chain would have meant answering to a session that happens to be present as well as, rather than instead of, the token; the route checks the token alone and ignores any cookie a request carries. It talks to Keycloak under two identities that never mix: the existing `safeLearn` client's own credentials to introspect the caller's token, and a second, `view-users`-only service-account client (`DIRECTORY_SERVICE_CLIENT_ID`/`_SECRET`) to query the Admin REST API — the calling teacher's or admin's own Keycloak access, whatever it is, is never used for the lookup itself. `docs-keycloak.md` names what the second client needs, and `test/checks/deployment-surface.js` and `test/checks/directory-search.js` assert both halves. How those credentials reach a deployed instance was the one part of this that nothing asserted, and for two changes running they reached none: every deployed instance answered 502 for this route while the plugin, which treats a refusal as "not logged in" on purpose, said nothing about why. The repair that followed put them in both of the two channels a deployment has, which are not equivalent — `site/.env` is copied into the image by the Dockerfile and read there by `dotenv`, and that image is pushed to a registry, so a secret in it sits in a published layer and outlives every rotation of it; `deploy/.env` is read by docker-compose on the server to interpolate `deploy/docker-compose.yml`, and reaches the container only for the names that file's `environment:` block passes on, which for these two it did not. So the half that worked was the half that should not have, and the half that should have was inert. They now travel by the container's environment alone. `test/deployment-config.test.js` now reads the workflow, the compose file and the application's sources together and fails when a variable the code reads reaches no deployed instance — for these two, and for every one added after them.

A real, LDAP-federated deployment (per `docs-keycloak.md`) would populate the first source instead of or alongside the second.

With *Strict line breaks* off — the default — a single newline is rendered as a break, so the runs of nodes between breaks are the lines the paragraph was written as, in order. That is how a directive line is found in rendered output at all, and it is what makes `#exam` inside a directive harmless: Obsidian renders it as a tag link of its own, so the line arrives as text, an anchor and more text, and a rule reading single text nodes would see three fragments of a directive and recognize none of them. With the setting turned on, a paragraph's lines are joined into running text and a directive that is not the paragraph's first line would keep its characters. The plugin does not read the setting; the case is named here rather than guarded, because guarding it means a second way of finding a line and the two would drift.

Measured in a running Obsidian, only one of them is laid out to a width of its own: a table widget carries `margin-inline: -16px; padding-inline: 16px`, so its box runs 16px wider on each side than the line above it while its content stands exactly where that line's does. The side edges and the tint are therefore background layers positioned against the element's *content* box, which is where they line up whatever that padding is; the horizontal edges are left on the element's box, where a table widget would draw them 16px too wide on each side. It cannot arise in a document anyone writes: both ends of both block kinds are their markers — `@@@` and `##side-by-side-start`/`-end` — and the editor renders a marker line as a line. Drawing them the same way would mean the same rule for a case that has no instance, so the divergence is written down instead. A theme that lays widget elements out differently again is out of scope for the same reason it is out of scope in `design.md`: the rule depends on no number, but a theme that puts the *content* somewhere else would need measuring rather than guessing.
- **The frame reaches those elements as a class written onto an element the plugin does not own, which is a second mechanism beside the decoration set.** From the same change, and the reason is that there is no first one: CodeMirror's `Decoration.line` needs a line, and Obsidian's widget is a sibling of the line elements rather than one of them. `view.posAtDOM` maps such an element back to the line it was built from, so what each line carries is decided once, in `markLines`, and applied twice — as decorations where the editor renders a line, and as a class on the element where it does not. Three things follow and are accepted. A `cm-gap` is skipped by name: it stands for the whole stretch the editor has scrolled away and built nothing for, one element covering many lines, and it answers `posAtDOM` with a real position — framing it by that line would paint a block's frame across an arbitrary part of the document. An element Obsidian rebuilds loses the class until the pass runs again, which is what the `MutationObserver` on `.cm-content`'s child list is for; a diagram and an embedded note both arrive after the update that produced their range. And the pass writes only classes `lineClasses` can produce, listed in `BLOCK_CLASSES` — a class added there and forgotten here would still be *applied*, because what is added comes from the map; what the list is for is taking one off again when a block stops covering an element.
- **The plugin resolves block state over the whole document on every rebuild, and that cost is accepted.** Also from `plugin-fix-editor-decorations`. Marking now rebuilds on a cursor move and a viewport change as well as on a keystroke, which is what the editor requires — in Live Preview a tag becomes editable when the cursor enters it, and the editor builds only the lines around the viewport, so scrolling brings in lines nothing has looked at. Decorations are produced for the visible lines only, but *which lines are inside a block* cannot be decided from the visible lines: a block opened three screens up still governs what is on screen. So the scan walks every line to resolve the blocks and then emits for the visible ones. Line iteration is cheap next to constructing decorations and the corpus is small, but on a very large document a whole-document walk per cursor move becomes noticeable. The alternative — maintaining block state incrementally across updates — is materially harder to get right and would need verification of its own. If it ever becomes visible, the fix is to cache the resolved blocks per document version; written down here so the trade-off is not rediscovered as a defect.
- **The plugin builds its context-menu submenu with `MenuItem.setSubmenu`, which the running Obsidian has and the published typings do not.** Recorded by the change `plugin-menu-submenu-and-icons`, which replaced the five flat entries the plugin used to write into the editor's context menu with one `SafeLearn` entry carrying them. Obsidian 1.13.7 defines `setSubmenu` on the object `Menu.addItem` hands out — it is what the application's own *Format*, *Paragraph* and *Insert* entries are made of — while `obsidian` 1.8.7 declares only `setTitle`, `setIcon`, `setSection` and `onClick` on `MenuItem`. So `main.ts` carries a `declare module "obsidian"` augmentation naming it, rather than an `as any` at the call site that would silence the rest of the expression with it, and asks `typeof item.setSubmenu === "function"` before relying on it. The guard is not about an old Obsidian — `minAppVersion` is 1.5.7 and submenus are older — but about where the code runs: inside the `editor-menu` handler, while a menu is being assembled for somebody who just right-clicked, where a `TypeError` can cost the entries other plugins were about to add. Where the call is absent the plugin writes the flat section it wrote before, so the bad day produces the menu that used to be there rather than a broken one; the answer is asked of a menu of the plugin's own and cached, so that it decides which menu gets built instead of being discovered halfway through building it. `test/obsidian/plugin.test.js` asserts the nesting rather than tolerating it, so a run under a version without the call fails loudly instead of passing on the fallback. A person reading `main.ts` against the API documentation would otherwise meet the call as a bug.
- **Two class names of Obsidian's own are relied on to read that menu back: `has-submenu` and `data-section`.** From the same change. A submenu's items are not in the document until it is open, and it opens on a hover that Obsidian does not accept as a dispatched `mouseover` — so `test/obsidian/harness.js` and `tools/obsidian-screenshots.mjs` find the entry as `.menu-item[data-section="safelearn"].has-submenu` and move the pointer onto it. The section is the plugin's own name and therefore its to rely on; `has-submenu` is Obsidian's, and it is not unique — the application's *Copy path*, *Paragraph* and *Insert* carry it too, which is why the section and not the class is what identifies the entry. Only the harness and the screenshot tool depend on either, so a rename in Obsidian costs a red run and a one-line fix rather than a broken plugin.
- **The plugin gained its own identity toward Keycloak, independent of the server's browser session.** Added by `plugin-admin-directory-ui`: a full Authorization Code + PKCE login against the school's Keycloak realm, completed in the system browser and returned through Obsidian's own `obsidian://<manifest-id>-auth` protocol handler rather than a loopback HTTP listener — the design rejects a loopback listener outright, since it needs a real TCP server that Obsidian mobile does not have. A new `PluginSettingTab` (the plugin had none before this) carries three settings: the safeLearn instance URL (empty by default, and everything below stays off without it), and a Keycloak URL / Realm pair defaulted to this project's shared identity provider — needed because `keycloak.json` is deliberately never served to a browser (`test/checks/deployment-surface.js`), so the plugin cannot discover its own realm's connection details remotely. Only the refresh token is persisted (`saveData`/`data.json`); the access token lives in memory only and is re-derived on load and before each directory call. The new Keycloak client this needs (`safelearn-plugin`, public, PKCE-only, no client roles of its own) is an operator-provisioned step documented in the plugin's own `README.md`, not something the plugin or a person installing it can do.
- **`GET /api/admin/directory/search` gained a UI on the plugin side, and one small server change to make "list classes" possible at all.** The "List classes" command and the directory picker `NameListModal` gained above its textarea (both gated behind a login, silently absent without one) share one fetch: every role/group value across the whole directory that is not one of `teacher`, `teachers`, `student`, `students`, `admin` — an accepted approximation, since the backend has no closed notion of "class" for the plugin to recover (an `examParticipant`-style marker is listed exactly like an actual class). That fetch needs an empty query to enumerate everyone, which the endpoint originally answered with `[]` — discovered mid-implementation, and resolved by having an empty or missing `q` return the whole directory instead (see the route table above and `specs/directory-search/spec.md` in the change). Nothing else about the endpoint changed.
- **The directory picker's class filter and result list became multi-select, and the picker now says whether the directory can be reached at all.** Added by `plugin-directory-multi-select`, built against a real school's directory rather than the handful of demo accounts the prior change was tested with. The class filter is a text `<input>` narrowing a list of `<input type="checkbox">` rows (replacing a `<select>` that did not scale past a school's actual class count) rather than a `<select multiple>` — the latter's ctrl/cmd-click gesture is not discoverable and would teach a person a second way to "mark several" beside the one the result list uses. Checking more than one class issues one `searchDirectory` call per checked class and unions the results client-side, de-duplicated by name — the server's one-query-string contract (`specs/directory-search/spec.md`) is unchanged; the client/server split is a deliberate trade-off, not a limitation discovered along the way. Result rows likewise gained a leading checkbox (replacing click-to-append) plus one "Add selected" control below the list — a plain `<div>` with a click handler, following `.safelearn-directory-result`'s own pattern, never a `<button>`, since `buildDirectorySearch`'s own constraint (the harness finds the modal's field and confirmation as its first `input`/`textarea` and its first `button`) still holds. Both the checked classes and the checked results survive a re-render (narrowing the class filter further, or a new search), keyed by name rather than by DOM node. *(The result half of this — the row checkboxes and "Add selected" — was replaced by `pick-people-by-moving-them`, two entries below; the class filter's checkbox rows are unchanged.)* `SafeLearnPlugin.searchDirectory` now reports `{ outcome: "ok" | "unreachable" | "failed" | "refused"; entries }` instead of a bare array that collapsed every failure to `[]` alike — a caught `requestUrl` exception is `"unreachable"`, a `403` stays `"refused"` (rendered exactly as "not logged in", `plugin-login-state`'s boundary untouched), any other `>=400` is `"failed"`. A status line above the query input, hidden for `"ok"`/`"refused"`, shows a short message for the other two — populated from the `classLikeValues()` fetch already made once per modal open, so no second request is added for it, and updated again after every search since a picker opened reachable can still have a later one fail.
- ~~**The plugin's real PKCE round trip is not covered by `test/obsidian/`, and cannot be from this harness.**~~ **Settled** by the change `plugin-login-flow`, and only half of it was ever true. Driving a real *OS-level browser* through an interactive Keycloak login is indeed outside a CDP-attached Puppeteer session, and still is. But nothing about the round trip requires one: the realm's login page is an HTML form and its answer is a `Location` header, so the harness walks both in Node's `fetch` (`completeRealLogin` in `test/obsidian/harness.js`) and hands the authorization code back through `app.workspace.protocolHandler.dispatch`, which is the same path Obsidian's own `obsidian://` handling takes. The plugin starts the login, so the verifier, the challenge and the `state` are its own, and the exchange and everything written to `data.json` stay the plugin's throughout — the harness delivers a browser's answer rather than standing in for the plugin. What this costs is stated below.
- **The plugin's login state is not readable from a status bar on mobile, and that is accepted rather than worked around.** From the change `plugin-login-flow`, which gave the login five named states and put the current one in a status-bar item so it can be read without the settings being open — a login concludes minutes after the click that started it, and by then a person is not looking at the settings tab. Obsidian shows no status bar on mobile, so that surface is simply absent there. It is accepted because the item was never the only place a state is readable: the Notice raised on every change of state and the settings tab's own block carry it on every platform, which is what `plugin-login-state` actually requires. The status bar is what makes the state readable *without* the settings on desktop, not what makes it readable at all. The alternative — a floating element of the plugin's own on mobile — would put a permanent widget into somebody's writing surface for a state that is *logged in* almost all of the time.
- **The plugin suite now reaches the network and uses the shared demo teacher account, for two checks and no others.** Also from `plugin-login-flow`. `test/obsidian/` was built to start no server and authenticate against nothing, and 89 of its checks still do neither: every state is reached through the plugin's own facts. Two cannot be. What the realm answers for `expires_in` is what the documentation records about this realm, and a login that actually completes from one end to the other is the one thing a stubbed access token cannot stand in for. Both are read from `auth.unterrainer.info` against the `safeLearn` realm, with the same `SAFELEARN_TEST_TEACHER_USER`/`SAFELEARN_TEST_TEACHER_PASSWORD` the server suite already uses, so one installation is still configured once. The cost is that `npm run test:obsidian` no longer passes offline. It fails loudly and names what it looked for rather than skipping, because `plugin-verification` asks for exactly that: a check that cannot reach a state must not report an empty pass.
- **The live view's stream reads the session from its store instead of through `req.session`.** Recorded by the change `exam-online-tests`. A request that stays open for a whole sitting holds the session as it was when it started; re-checking through `req.session.reload()` would have the request write that session back when it ends, over tokens another request renewed meanwhile. So `exam/routes-live.js` asks the store for a copy before every event and heartbeat and builds the permission context anew from it - one account lookup at the identity provider per check, for a handful of teachers. A token within 60 s of its expiry is not renewed by the stream at all: it sends `renew`, the client reconnects, and that ordinary request renews it the way every request does.
- ~~**An image kept for an old snapshot is linked to every later test of its question too.**~~ **Settled** by the change `exam-questions-follow-pool`: a copy links exactly the images its texts reference (`linkImages` in `exam/tests.js`), and an image a begun test still shows keeps its `question_id` until the question is deleted, then `NULL`, and goes once no test shows it. Recorded by the change `exam-question-editor`. A save deletes a question's images that its texts no longer reference, except those a `test_image` row holds: those stay, so a written test still shows the picture its snapshot names. `snapshot()` in `exam/tests.js` links images by `question_id`, not by what the texts reference, so a test assembled after such an edit links the old image as well. Nothing shows it - no text of the new snapshot names it - and a student could only fetch it by guessing its id during an open attempt, which then reveals an earlier version of a question in the same test. It was left so because the change reuses `updateTest` and the snapshot unchanged (design D8); linking only the referenced images is a local change in `snapshot()` if it ever matters.
- **An attempt is bound to a cookie, not to the express session.** Also from `exam-online-tests`. Sessions live in the process's memory and die with a restart; the attempt's `sl-attempt-<id>` cookie and the hash of its secret in the database do not, so a restart during a sitting costs a student a silent single-sign-on round trip and nothing else. The harness proves it by restarting its own instance (`restartApplication`, `reauthenticate` in `test/harness.js`), the one check that does.
- **A login in progress reads as failed the moment its lifetime passes, and is dropped a tick later.** From the same change. The state is derived and has no side effects, so it cannot delete anything; the expiry runs on a `registerInterval` timer, one second apart, so a status-bar item corrects itself without anybody opening the settings. Between those two the entry still exists while the state already reads *login failed*, which is deliberate — the alternative is a second in which a login that has run out reads as still running. `handleAuthCallback` reads the entry's own lifetime rather than trusting the sweep to have happened, so a callback landing in that second completes nothing; a login that succeeded or failed depending on which second its answer arrived in would be the worst of the three possible arrangements. The lifetime itself is the plugin's own ten minutes (`LOGIN_DEADLINE_MS`), sized for a person at a login page. It was briefly taken from the realm's `refresh_expires_in`, which measures a session and not a person: a realm answering `1` on a refresh at the end of a session locked an installation out of logging in for good, and nothing bounded the value from below. See `docs-keycloak.md`.
- **The directory search endpoint stopped holding a request open across a multi-minute fetch, and a `2xx` from it no longer implies a result array.** From the change `show-directory-fetch-progress`. Against the school's own realm (~14,000 LDAP-federated users) a cold cache meant minutes inside one `requestUrl` with nothing to show — and a reverse proxy in front of a deployment severs an idle request long before that, so the blocking wait was not merely invisible but not reliably survivable either. The route now answers `202` with the fetch's progress when it has nothing to match against, and `200` from data past its 10-minute TTL with the refresh started behind the answer rather than in front of it: the TTL says when to *start* refreshing, not when to stop serving, and re-entering "nothing is happening" every ten minutes on a realm edited by hand a few times a year would trade the reported problem for a worse one. A new `GET /api/admin/directory/status` reports the same payload without transferring anything, behind the identical gate. The two callbacks the fetch already fired per page and per resolved user — which until now only wrote log lines — became the source of that progress, so nothing about the fetch itself changed to make it observable. **Version skew was decided in both directions rather than gated behind an opt-in parameter:** an old plugin reads a `202` as "The directory search failed." (its `!Array.isArray(body)` branch), which is worse wording than the new path but better than the current silent hang and resolves itself once the fetch completes; a new plugin reads the status endpoint's `404` from an old server as "state unknown" and waits on the search as it always did. A query parameter preserving the blocking path would have preserved the bug it exists to remove.
- **The plugin polls the status endpoint rather than re-issuing the search, and the poll is bounded.** Also from `show-directory-fetch-progress`. Re-issuing the search every two seconds would risk materializing and transferring some fourteen thousand entries per tick; the status endpoint reads process memory and answers a handful of numbers. If the status reports no fetch running while the plugin still holds a `202`, that is a fetch that died — the plugin re-issues the search exactly once more and falls back to its ordinary failure indication if that also comes back `202`, so a fetch that keeps dying can never become an endless poll. The progress is rendered from raw per-phase figures the server reports, not from one blended percentage: the pagination pass dominates on the demo realm and the role-mappings pass on the production one, so any weighting chosen here would produce a bar that stalls and then leaps — precisely the "is it broken?" impression the change exists to remove.
- **People are picked by moving them into a visible list, and the picker replaced the free-text field rather than sitting above it.** Added by `pick-people-by-moving-them`. The result rows lost their checkboxes: clicking a row moves that person into a chosen list below the results, clicking them there takes them back out, and "Add selected" became "Add visible", which takes exactly what the result list is currently rendering (`lastEntries` — the union of every checked class) rather than a marked subset of it. That is the change's whole point: narrowing to a class and taking it over cost one click per person, roughly thirty for a real class, and the one case the class filter exists to serve was the one the picker made most tedious. The checkboxes also hid the selection — `checkedResultNames` deliberately survived a filter change, so "Add selected" could carry names the current filter no longer showed, with nothing in the dialog saying so and no way to see or undo a mark that had scrolled away. `NameListModal.chosenNames` (insertion-ordered, deduplicated on the trimmed exact name) now replaces both that set and the textarea as what the dialog returns: insertion order because the commands write one section per name in the order given, the trimmed exact name because `plugin-authoring-commands` writes the name as given and folding it here would only have to be undone when writing. **This is breaking for the dialog's shape where a picker is shown** — the free-text field is gone, and a name the directory has no entry for is written into the document afterwards rather than typed into the command, which is the user's own preference recorded here because it is a trade, not a cleanup: a guest is now named in the document instead of in the dialog. Where no picker is shown (no instance configured, or no login held) the dialog is unchanged, and the field is additionally *revealed* where the picker reports `unreachable` or `failed`, since a dialog that can offer nobody and takes no typing would be a dead end; `confirm` reads both sources, deduplicated, so a picker that goes unreachable after somebody has been chosen does not drop them. Ctrl/Cmd+Enter moved from the textarea to the modal's content element for the same reason — the binding cannot live on a field that is not there — while a plain Enter stays unhandled and so goes on belonging to the list inside the textarea where that is shown.
- **Chosen people are written in surname order, decided at `confirm`, while the picker keeps the directory's order.** Added by `sort-and-prefill-the-sections-per-name`. `NameListModal.chosen` holds `{ name, firstName?, lastName? }` in insertion order — the directory's order when a class is taken over, in which a class stands together while it is being picked, which is what the user asked to keep — and `orderForWriting` sorts it once, on confirm, by surname then given name with a module-level `Intl.Collator("de", { sensitivity: "base" })`, typed lines following in their own order. The surname comes from the server (`searchDirectory` now answers `firstName`/`lastName` beside `name`), because splitting `name` at its last space misfiles every two-word surname; an instance older than that sends neither, and the plugin falls back to ordering by display name. The same change gave the per-name dialog an optional content field written into every section in place of its blank line (`sectionContentLines`), refusing content with a line `directiveOpeningPattern()` matches, since that line would close the section and leave the rest of the content outside it.
- **The directory picker became a component of its own, and the search hands back the e-mail address.** Added by `invitation-list-from-directory`. `buildDirectorySearch` and its `chosen`/`fetchWait` state moved out of `NameListModal` into `DirectoryPicker` (constructed with the plugin and a container; exposes `chosen`, calls `onChange` and `onUnavailable`, `dispose()` ends the fetch wait), because a second dialog — "Invitation list…" — needed the same search, class filter, "Add visible" and fetch wait, and shares nothing else with the per-name dialog. `ChosenPerson` now carries the whole entry (`email` and `roles` too), and the surname sort was split out of `orderForWriting` as `sortBySurname`, so both commands order by one rule. The invitation list is one pure function, `formatInvitationList(people, format)`, called by the preview, the insert and the copy alike; the four texts are stored as typed (`,,\n`) and resolved by `unescapeFormatText` in one left-to-right pass, and the format is persisted in `data.json` (`invitationFormat`) on either confirmation only. On the server, `searchResultEntry` gained `email` — a deliberate widening of what the endpoint discloses, which until then returned nothing the display name did not show. Nothing was fetched additionally: the cache already held the full Keycloak user.
- **The harness stopped finding the name-list dialog's field by position, which the change above made unavoidable.** From the same change. `answerNameList` and `dialogBoxes` (`test/obsidian/harness.js`) located the field as the modal's first `input`/`textarea`; removing the textarea moves that first input to the picker's *search* field, so the convention did not merely shift but started answering the wrong element. Both now locate the picker through the `safelearn-` classes it already carries for exactly this purpose (`data-safelearn-name` on result rows, and now on chosen rows), and keep the textarea path for the no-login and fallback cases. `answerNameList` therefore answers a picker by *choosing* each name from it and fails loudly on a name the directory does not hold, which is the truth about that dialog; `confirmNameList()` is what a check that only wants the dialog shut uses. The older constraint survives in a narrower form: the modal's confirmation is still its first and only `<button>`, so nothing inside the picker — rows, chosen rows, "Add visible" — may be one.
- **`executeCommandById` does not consult `checkCallback`'s return value at all.** Found while writing the check above: Obsidian's command dispatch calls a command's action directly and reports success unless it throws, regardless of what `checkCallback` returns — confirmed empirically by running `list-classes` through it with `checkCallback` forced to return `false`. `checkCallback(true)` ("checking, don't run") is what the command palette and the hotkey manager actually call to decide whether to offer a command; a check about a command being "not shown" has to ask that directly (`commandIsAvailable` in `test/obsidian/harness.js`), not whether a raw `executeCommandById` call was accepted.
- **The search's keyboard navigation keeps the focus in the field and marks the selection instead of moving it.** Added by `search-keyboard-navigation`. The alternative was a roving `tabindex` that moves real focus onto each result anchor; it was rejected because typing would then have to be routed back to the field by hand, and typing has to go on refining the query while a result is selected. The consequence is that `←` and `→` mean the tree rather than the caret while something is selected, which is why `↑` at the first result and `←` on a result that is not open both hand the selection back and put the caret at the end of the query — the one position from which `→` means the list again. The walk order is derived on every key press out of the DOM (`a.sl-search-name, a.sl-search-heading` minus anything inside a `collapsed` container) rather than kept beside it, so an expand and a collapse have nothing to invalidate and a node that is not displayed cannot be walked onto. Expanded-or-not stayed the one class pair the chevron already toggled, now written by a single function with two callers.
- **Select-on-focus is decided by the pointer of the press, not by what the machine can do.** From the same change. `pointerdown` records `event.pointerType`, the `focus` that follows reads and clears it: `touch` returns and does nothing at all, anything else — including an absent record, which is Tab — selects the field's content. `matchMedia("(pointer: coarse)")` was rejected because it describes the machine rather than the interaction, so a laptop with a touchscreen would get one behaviour for both of its pointers. The companion `mouseup` guard that keeps the selection from being collapsed is held to the mouseup of the focusing press and to a press that did not travel more than a few pixels, because a press that travelled is a drag and a drag must select what was dragged across.
- **Ending and extending a sitting rewrite the running attempts' deadlines, because a deadline is stored, not derived.** Recorded by the change `exam-ui-consistency`. Its design assumed the sweep would follow a moved window on its own; `startAttempt` however stores `min(start + duration, window end)` in `attempt.deadline`. End therefore sets every running deadline to now before `finalizeDue`, and Extend sets each to `min(started_at + duration, new closes_at)`. The window change is announced on the live channel without a participant, and the live view fetches a fresh snapshot instead of patching one row, since every deadline may have moved.
- **The directory-service client writes one thing: a course's Matura role.** Recorded by the change `exam-participant-role`. Until then read-only by design, it now also holds `manage-users` and `manage-clients`, for `setClientRoleHeld` alone: `GET clients?clientId=` (the internal id cached per process), `GET clients/<id>/roles/<name>`, on a first grant `POST clients/<id>/roles` (a 409 counts as success), then `POST`/`DELETE users/<uid>/role-mappings/clients/<id>`. The user's id comes from the held directory, else from one `GET users?username=&exact=true`, never from paging. A 403 becomes `DirectoryWriteRightsError` (`create` or `map`), answered to the teacher as a `409` naming the missing setup. After a write the held entry's `clientRoleNames` is patched and the disk cache rewritten, so every view shows the change on its next load; a student's own token carries it from their next login. The highlight is computed on the server from the held directory and travels with the answers the views already load - no view asks a second time; `css/exam.css` colours it with `--sl-exam-participant-bg`/`-fg` for both themes.
- **Rescheduling a sitting that is over deletes its attempts, and only an admin may delete any.** Recorded by the change `exam-reschedule-sitting`. `rescheduleSitting` (`exam/tests.js`) is separate from `updateSitting`, whose `requireNotOpened` and make-up duration rules would need exceptions. It keeps the duration and the `makeup` flag, so no make-up rule is touched, drops participants who have left the roster (`emptyRoster` if none is left), and in one transaction deletes the sitting's attempts (their rows go by `ON DELETE CASCADE`), moves the window and calls `refreshUsageDate`; the gradebook column follows by `MIN(opens_at)`, across a semester boundary too. With attempts the request needs an admin (`ForbiddenError`, `403`, the module's one refusal of that status that passes the gate) and the confirmed `attempts` count, so the second click's label is never exceeded. The route announces a `deleted` per attempt and a `window` on the live channel and `notifySittings` to the students' streams. Once a test's last attempt is gone, `testStarted` is false again and its questions are editable; since the change `exam-questions-follow-pool`, a test left with no attempt and no opened sitting also takes the pool's current version again and follows it (`followPoolIfNotBegun`).
- **A test's copy follows the pool until the test begins; then it is the snapshot.** Recorded by the change `exam-questions-follow-pool`. Every reader - page, preview, attempt start, scoring, lists, gradebook, live view - reads only `test_question`/`test_answer`, and none needs to know whether the test has begun. "Begun" is a query (`testBegun`: an attempt, or a sitting with `opens_at <= now`), not a column, so nothing has to happen at the moment a sitting opens: the copy as it stands then is the snapshot. A pool write that skipped `writeContent` would let a test not yet begun drift from the pool; the guard test fails on it. Deleting a question is always allowed: in a begun test the row's `question_id` becomes `NULL` and the admin's correction works by row id. In a closed year the triggers of migration 011 let exactly that unlinking and the usage deletion through.
- **The category tree drags with Pointer Events and a controller of its own, not HTML5 drag-and-drop or a library.** From the same change. `draggable` does nothing on a touch screen and teachers use tablets; the module loads no third-party client code, and the subset needed (into, before, after; auto-scroll; a 300 ms press on touch so a swipe still scrolls) fits in `exam/client/tree-drag.js`. Cut and paste by keyboard does the same moves, and covers questions too, which indent/outdent would not.
- **A destructive action asks by a second click on the same button, never by `window.confirm`.** From the same change. `confirmButton` in `frame.js` replaced four kinds of confirmation; it disarms on blur, Escape and after 5 s. The live view redraws a row on every change event, which disarms a button armed in it - an admin's Delete attempt during a busy sitting may need its two clicks in quick succession.
